# Turn 的完成与后台任务等待

状态：已确认的实现设计。按第 8 节拆分实现与验证。

## 1. 设计结论

区分「工作完成」和「暂时需要等待结果」，由模型明确表达意图，runtime
负责等待与恢复：

| 动作 | 职责 |
| --- | --- |
| `job_output(job_id, offset?)` | 立即读取日志和状态，不等待 |
| `job_wait(job_ids)` | 当前工作未完成，等待指定后台任务的结果；用户输入可以打断等待 |
| `finish(answer)` | 当前工作已经完成，结束 turn |
| `job_stop(job_id)` | 停止不再需要的后台任务，沿用现有行为 |

第一版假定模型能够合理理解提示、修正参数并选择工具。不引入重复回答检测、
无进展评分、自动切换策略或额外的重试预算。参数校验、取消、事件竞态和现有
执行预算仍由代码保证，不能依赖模型处理。

等待保持在同一个 turn 内。完成通知自动恢复的是正在等待的执行，
不是已经 `finish` 的工作。不新增「任何 runtime_notice 都启动一个新 turn」的调度规则。

### 取舍依据：健壮性与可理解性

这里的简化是减少策略，而不是省略正确性保证。模型负责判断任务是否完成；
runtime 负责正确执行这个选择，即使事件恰好同时发生。

| 选择 | 健壮性收益 | 可理解性收益 |
| --- | --- | --- |
| 显式 `finish` 不因活跃 job 被拦截 | 长期运行的服务不会迫使 turn 永远等待 | finish 始终表达完成，不暗中变成 wait |
| 纯文本、有活跃 job 时提示明确选择 | 减少无意结束、丢下尚需处理结果的情况 | 不把普通文字猜成「等待」或「放弃结果」 |
| `job_wait` 等待指定任务 | 无关后台任务不会无限延长一次等待 | 模型和用户都知道正在等什么 |
| 保留当前 turn，只挂起异步执行 | 复用取消、作用域、输入处理和预算，不新增跨 turn 恢复竞态 | 等待是当前工作的一个阶段，不是假装完成后再启动 |
| 第一版不设等待 timeout | 避免超时导致无结果的反复模型往返 | 等事件，不猜时长；用户可随时输入或取消 |
| 不重启已经完成的 turn | 避免迟到通知重新启动用户认为已经结束的工作 | 记录通知与继续工作是两件不同的事 |

不选择两种看似更省代码的做法：无条件阻止有后台任务的 `finish`，以及任何
完成通知都自动启动模型。前者混淆完成与等待，后者需要额外解释取消、迟到
通知、重复启动和新用户任务之间的关系。

第一版明确不保证模型永不重复无效回答或查询；这不是一个已有可靠保证被
移除，而是暂不新增通用的无进展治理。若实际日志证明存在问题，再单独设计。
同时，无效参数不能让等待挂死，合理调用遇到并发事件不能丢输入，取消不能
失效——这些属于本次必须验证的健壮性。

## 2. 当前行为与问题

目前 `AgentLoop::run` 正常完成有两个入口：模型返回不含工具调用的回答，
或者调用 `finish`。两条路径都会检查已经排队的 steering input；有新输入时
继续执行，否则经过现有 goal、review 和上下文收尾流程，最终写入
`Terminal(Finished(...))` 并发出 `AgentFinished`。

当前不会因为仍有活跃的后台任务而要求模型明确选择。任务尚未结束、通知尚未
到达时，纯文本回答就可能结束 turn。

`job_output.wait_ms` 提供有时限的等待，但日志显示模型会连续调用它，形成
「等待两分钟、返回 running、再等两分钟」的长轮询。它也不以用户输入作为
结束等待的条件。

完成通知已经会进入会话，但 `serve` 空闲时只保存并展示通知，不自动发起新的
模型请求。一次性 `run` 则会在执行作用域结束后收尾，后台任务无法依靠以后
的通知继续完成原工作。

## 3. Turn 的正常完成规则

以下规则只调整模型主动完成的路径。用户取消、`Abort`、异常、步数耗尽和
上下文预算退出继续遵循现有规则。

| 模型返回 | runtime 行为 |
| --- | --- |
| 纯文本，没有工具调用；没有活跃后台任务 | 沿用正常完成流程 |
| 纯文本，没有工具调用；有活跃后台任务 | 保存回答为普通 assistant 消息，加入后台任务提醒，再请求模型 |
| 显式 `finish` | 不因后台任务仍然活跃而拒绝完成；沿用现有新输入、goal 和收尾检查 |
| `job_wait` | 校验参数，在当前 turn 内进入事件等待 |
| 其他工具调用 | 正常执行 |

已有用户输入或完成通知时，优先沿用现有 steering 路径处理，不在同一步重复
插入后台任务提醒。提醒前重新检查任务状态，不能只看模型请求发起时的快照。

后台任务提醒示意：

> 仍有后台任务运行：bg-1（测试）、bg-2（构建）。如果工作已经完成，调用
> finish；如果还需要它们的结果，调用 job_wait；也可以继续其他工作，或用
> job_stop 停止不再需要的任务。

提醒作为 `RuntimeNotice` 写入，不伪装成用户的新请求，不创建新 turn。
它只用于消除「纯文本是否意味着完成」的歧义，不能再次拦截随后的显式
`finish`。第一版不做「提醒后仍返回纯文本则强制等待」等兜底状态机；如果模型
继续返回纯文本且任务仍活跃，仍适用同一规则。这种不遵循提示的循环暂不在
本次范围内，现有执行限制保持有效，但默认 `max_steps` 为 `Int.MAX_VALUE`，
不能把它视为实用的重复回答防护。本版仍不以第二次纯文本自动完成来替代明确选择。

完成提醒只针对本 turn 开始后新登记、仍未完成发布的 job。loop 创建时记录
registry 中已有的 ID；先前 turn 留下的服务不触发本 turn 的提醒，避免无关回答
每次都多一次模型请求。旧任务仍可显式 job_wait；这项过滤只作用于完成提醒。
同一会话恢复后也不自动推断旧任务是否仍是当前工作的依赖。
已完成的历史 job 不阻止正常完成。
任务的终态、完成通知发布和等待唤醒必须协调，避免任务刚结束却尚未发布通知
时，完成检查从间隙中穿过。不能只用一个提前递减的计数代替这个条件。

## 4. `job_wait` 的接口与行为

调用示例：

```json
{"job_ids":["bg-1","bg-2"]}
```

- `job_ids` 必填，必须是非空字符串数组；空 ID 和未知 ID 报工具错误。
- 校验全部 ID 后才开始等待，不能因为其中一个已结束而忽略另一个无效 ID。
- 重复 ID 去重，保持首次出现顺序。
- 第一版不提供 `timeout` / `wait_ms`，不让模型猜等待时长。
- 目标中任意一个已经终止，立即返回目标任务的状态；终止包括退出和停止。
- 否则等待任一目标终止，或用户输入到达。新的日志内容本身不结束等待。
- 返回等待结束原因和目标状态，不读取整份日志；日志由 `job_output` 读取。

返回原因分为「目标任务已终止」和「用户输入打断等待」。取消不作为普通成功
结果返回，而是沿用当前 turn 的取消及 `Interrupted` 路径。任务失败的状态必须
保留，但 `job_wait` 本身的等待成功不等于后台程序执行成功。

模型可以在一个任务完成后处理其结果，再对剩余任务调用 `job_wait`。
这属于有事件驱动的后续等待，而不是超时轮询。

## 5. 等待如何实现

`job_wait` 返回专用的 agent 控制动作，由 agent loop 执行等待。工具定义负责
参数解码，loop 与后台 registry 负责状态、输入与取消的协调。不要把用户输入
队列的消费权交给独立的普通工具执行器。

第一版要求 `job_wait` 单独出现在一个工具批次中。若同批还包含其他调用，
给 `job_wait` 记录可修正的工具错误，不进入等待；其他调用按现有批次规则处理。
等待动作不能进入普通工具的并行预执行路径。

等待过程中：

1. 当前异步 turn 保持存活，但不再发起模型请求，也不消耗新的模型步骤。
2. 后台进程、输出读取器和 `serve` 命令循环继续运行。
3. 等待任一目标任务终止、用户输入到达或当前执行被取消。
4. 恢复时先完成本次工具结果的记录，再按现有路径记录和应用排队输入，
   最后才发起下一次模型请求，保持工具调用与结果配对。

用户输入包括发给当前 turn 的 prompt steering，以及应由当前 turn 处理的
command context。用户设置或清除 goal 时，Notice 保持原有持久化格式，但
入队时显式标记为可唤醒输入；普通 job Notice 不唤醒等待。
若 goal 排在其他 prompt 或 compaction 之后，则仍遵循既有 wire 顺序，
不会提前应用或用它唤醒当前 turn。
`serve` 的普通 `Prompt` 命令仍遵循既有排队语义；本改动不
把排队的新任务自动转成 steering。桌面的当前任务补充输入应走现有 steer 路径。

其他 job 的完成通知保留在队列中，不丢弃；仅有非目标 job 完成时不要求
结束本次等待。实现可以使用合并唤醒信号，但唤醒后必须重新判断条件，不能把
信号当成输入本身。普通通知不额外创建模型执行。

实现必须保证：

- 先建立可观察的等待机制，再检查状态，或使用等价的无丢失唤醒协议。
  完成在检查前、检查后或挂起同时发生，都不能漏掉。
- 用户消息仍留在原有的无损队列中，由 loop 正常消费、持久化。
- 退出等待时清理未获胜的监听；取消监听不能取消它观察的后台进程。
- 目标被主动停止时也能唤醒。不能只依赖自然结束通知，因为现有 `job_stop`
  不发送重复的完成通知。
- 完成通知沿用现有发布路径，不能由 waiter 再造一份。
- 取消优先遵循现有异步取消机制，不因另一个完成事件到达而启动下一次请求。

不新增持久化的 Waiting 会话状态，不实现进程重启后的等待恢复，也不重置
当前 turn 的上下文、步骤或其他预算。明确的执行限制可以终止尚未完成的工作；
等待不能绕过它们。最后一个允许的模型步骤不应进入无法再处理结果的等待，
应按现有预算终止语义收尾。

## 6. CLI 与桌面的生命周期

| 场景 | 行为 |
| --- | --- |
| 一次性 `openseek run` 正在 `job_wait` | turn 和作用域存活，进程不因模型暂时无事可做而退出 |
| 一次性 `run` 真正完成、取消或失败 | 按现有作用域规则收尾，后台任务随之取消 |
| `openseek serve` 正在 `job_wait` | 当前 turn 保持活跃，继续接收 steering 和取消命令 |
| `serve` 的 turn 已显式完成 | 服务进程保留；后台任务按既有生命周期运行，之后的通知记录到会话，但不重启已完成的工作 |

显式 `finish` 只声明不再等待结果，不承诺后台进程在 CLI 退出后继续存活。
本次不新增 daemon / 脱离进程作用域的运行方式。CLI 的 stdin 也不因此变成
交互式消息通道；`run` 的取消仍使用既有进程取消机制。

桌面应保持当前任务为执行中，等待时显示目标 job ID，输入和取消仍可用。
优先利用现有工具活动展示；若不足，只补充等待活动事件及对应展示，不引入
新的 run ID、自动启动握手或宿主调度流程。

## 7. 测试与验收

真实 CLI 测试由 `just test`（或单独 `just test-turn-finish`）和 native CI 执行。

使用可控的后台任务、事件队列和本地假模型服务测试，不依赖在线模型或长时间
sleep。超时仅作为测试失败的上限，不作为生产等待机制。

| 测试 | 必须观察到的结果 |
| --- | --- |
| 纯文本结束，无活跃任务 | 正常写入 Finished |
| 纯文本结束，有活跃任务 | 回答保存为普通消息，提醒包含 job ID，没有提前 Finished |
| 提醒后显式 `finish` | 可以结束，不再次被后台任务拦截 |
| `job_wait` 的无效参数、未知 ID、混合批次 | 明确报错，不挂起，不留下未配对的工具调用 |
| 目标已经结束 | 立即返回状态 |
| 目标在检查与挂起之间结束 | 正确恢复，没有丢失唤醒 |
| 多目标中一个完成 | 返回一次，其他 job 继续执行 |
| 非目标 job 完成 | 通知保留，不误判目标已完成 |
| 目标被停止或 watchdog 终止 | 等待结束，状态和停止原因正确 |
| 等待期间用户 steering | 不等目标完成就恢复，消息不丢失、不重复 |
| 等待期间取消 | Interrupted，没有后续模型请求，监听清理完成 |
| 一次性 CLI 闭环 | 启动 job → 选择等待 → 完成通知 → 读取结果 → finish；作用域在最后才结束 |
| 步数或上下文预算边界 | 不重置、不绕过现有预算，不留下未完成的工具批次 |

至少一个闭环测试必须检查实际第二次/后续模型请求中的消息，证明完成通知
确实进入模型上下文，而不只是验证通知入队。等待期间模型请求次数应保持不变。
桌面补充输入和取消需要验证实际事件路径，而不只是输入框看起来可用。

实现完成后按仓库要求运行 `just check`、`just test`、`just build`，最后更新
并检查生成接口与格式；涉及桌面展示时补充相应宿主/前端测试。

## 8. 两个 stacked PR

### PR 1：明确 turn 完成与事件等待

- 新增 `job_wait` 控制动作及注册、描述和参数校验。
- 为纯文本完成增加活跃后台任务提醒；显式 `finish` 不被这项提醒阻拦。
- 实现同一 turn 内的可取消事件等待，支持目标终止和用户 steering。
- 验证一次性 CLI 的作用域、桌面输入/取消，以及上述竞态。
- 更新提示词，解释完成、等待与读取的分工；暂时保留 `job_output.wait_ms`。

这个 PR 将最初设想的「空闲时自动新开 turn」收敛为「工作未完成时显式等待，
在同一个 turn 中由事件恢复」。这是本文的设计选择，避免完成后的自动重启问题。

### PR 2：移除 `job_output.wait_ms`

- 以 PR 1 的分支为 base，移除等待参数、解码和执行分支。
- 更新工具描述、提示词、文档、生成接口和相关测试。
- 把原有依赖等待的测试改为明确等待任务后立即读输出。
- 保留 tail、offset 分页、日志保存和错误分类行为。
- 验证不携带等待参数的调用立即返回，不再有模型按时间反复等待的指引。

先前实验性的「有 job 就自动阻止 finish」方案不属于本设计。
